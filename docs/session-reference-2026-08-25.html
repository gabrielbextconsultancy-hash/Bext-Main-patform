What the self-healing agent does

Four rings on top of the regression registry that already existed. Full detail in docs/SELF-HEALING.md.

Ring 0 — Detect

Uptime Kuma. HTTP, TCP and DNS checks, plus one push deadman per scheduled workflow — the only thing that sees a workflow that is active and not running.

live

Ring 1 — Diagnose

heal-rules.js is REGRESSIONS.md as data: 14 rules, each sharing an id with its preflight check and its written section. One fact, three views.

live

Ring 2 — Remediate

Six reversible actions, rate-capped, written to the incident log before they run. Container restarts pass two independent gates; Premier Fitness is unreachable by design.

live

Ring 2.5 — Validate

Actions are recorded attempted, never healed. Next cycle the healer checks the workflow actually recovered, and escalates a fix that did not hold.

live

Ring 3 — Learn

An unknown failure escalates to Teams with its signature. You diagnose once; the rule, the check and the write-up land in the same commit. Coverage grows.

live

Validation — Contract Test

02:00 nightly, three hours before the client report. Asserts what only the running container can see: env, sandbox limits, code that parses, heartbeats present.

Three things worth remembering

Each cost real time, and each is now guarded by an assertion rather than by memory.

A green build is not a deployed change

The repo nests services under infra/ with build: ../dashboard; the VPS layout is flat, and CI rewrites the path on the way over. Shipping the compose by hand skipped that rewrite, so Docker built /docker/dashboard — a stale copy that still existed.

Every rebuild succeeded and changed nothing, which is exactly what made it expensive. Guarded by R032 / R032b.

The sandbox is not Node

The self-healer shipped twice with faults only a real run could find: $env.N8N_URL is not set inside the container, and the Code sandbox exposes neither fetch nor http. Both compiled clean.

Nothing was committed until a live run passed — that discipline is why the healer works rather than merely deploys.

A monitor that cries wolf gets ignored

Fixing the escalation path meant 136 already-logged failures would have posted to Teams, then re-posted every 15 minutes. Two guards went in first: an execution is never re-escalated, and a persistently broken workflow is recorded every cycle but announced once.

The same reasoning put the Graph Health heartbeat before its IF node rather than after — anchored after, it would have pinged only when Graph Health was broken.

Approved plan — next

An /architecture page showing the whole estate and every workflow inside it, generated from the workflows themselves so it cannot drift.

  1. Generatorn8n/build-architecture.js reads all 14 workflow JSONs and derives triggers, node order, actors and the tables each reads and writes. Workflows are linked where one writes a table another reads — nothing hand-listed.
  2. Excalidraw skillInstalled at project scope with the BEXT palette. Diagrams are editable, and the skill renders and inspects its own output to catch overlaps.
  3. DiagramsOne estate map plus one per workflow, in docs/diagrams/.
  4. The page@excalidraw/excalidraw embedded so the map pans and zooms, and element colours are patched from live incidents — a failing workflow is red in the diagram itself.
  5. GuardsA preflight check regenerates the graph and fails if it has drifted from the committed copy.
